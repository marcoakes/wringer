# The ACP auth handshake, measured — 2026-08-24

*A capture. Three agents on the author's Mac, every reply below verbatim from
`scripts/acp-authenticate-probe.py`. **No paid turn was sent**: everything here
is `initialize`, `authenticate` and `session/new`. Law 8: this page is not
edited to match a later tree; a correction goes below it with a date.*

## Why this was measured before anything was specified

Fable's R2 (`~/Claude/WRINGER_LEVELUP_RULINGS_2026-08-22.md`) rules that
Wringer's ACP client should implement the protocol's auth handshake — declare
the capability at `initialize`, read `authMethods`, drive `authenticate` with
the operator's declared credential — and that it is **spec-first, because it
touches the consent boundary.** Four rounds of the hunt died to mechanisms
that looked right when read, so the mechanism was executed first.

## THE FINDING: a successful `authenticate` proves NOTHING

**Measured on two independent vendors' agents, in opposite ways:**

- **`kimi-code acp` accepts its OWN advertised method id and stays
  unauthenticated.** `authenticate {"methodId": "login"}` returns no error —
  success, by JSON-RPC semantics — and the very next `session/new` still
  refuses with `-32000 Authentication required`.
- **`dcode --acp` returns `result: {}` for a method it never offered and does
  not implement.** Any id at all is accepted.

So a client that reads "`authenticate` returned without an error, therefore we
are authenticated" is wrong on both. **The only evidence of authentication is
what happens NEXT** — a `session/new` that succeeds where it previously
refused. That is red-before/green-after applied to the handshake itself, and
it is the same rule this whole project is about, arriving at the transport
layer.

## THE SECOND FINDING: nobody offers a credential-driveable method

R2.3 says "drive `authenticate` with the OPERATOR'S declared credential".
**Measured: no agent in this census offers a method that takes one.** Two
advertise nothing at all, and the one that advertises a method advertises an
interactive terminal login — a person's act, and one Wringer must not perform:
`worker_auth.refusal` already states that Wringer never logs an agent in,
because a login is somebody's account. Kimi's `_meta.terminal-auth` block even
carries a `command` and `args` for Wringer to run, which is **arbitrary code
from the agent, executed on the operator's machine** — the offer must be
SHOWN, never taken.

## THE THIRD FINDING: the advertised set does not depend on the client

Sequence L's belief was that `authMethods` is advertised "based on client
capabilities and a CLI flag". Measured across three client-capability shapes
per agent — `fs` only, nothing at all, and `fs` + `terminal` — **the set is
identical in all three for all three agents.** So "this agent offers no
methods" is a fact about the agent, not about our request.

## What this capture does NOT claim

Three agents on one Mac on one day. Gemini CLI and Goose are in the census and
were not installed here, so the client-capability finding is measured on three
agents rather than on ACP. `kimi-code` was signed out throughout; a signed-IN
Kimi was never measured, so what `authenticate` returns to an already-
authenticated agent is unknown. And every agent here was asked in English over
one protocol version.

## The probe's own defect, found by running it

The first version of `scripts/acp-authenticate-probe.py` checked its deadline
BETWEEN reads and then called `proc.stdout.readline()`, which blocks forever on
an agent that opens its pipes and says nothing. **It wedged for fourteen
minutes against a twenty-second ceiling on `kimi-code acp`** — the exact defect
`tests/test_timeout_never_grants.py` exists to refuse, in the instrument
written to measure the surface that rule is about. It reads on a thread now.

*Correction below the capture, not an edit to it (Law 8).*

**2026-08-24, same day, found by driving the BUILT client against the real
agent — the two method lists are NOT the same list.**

`kimi-code acp` sends the methods twice, in two different shapes, in one
exchange:

```
at `initialize`          "_meta": {"terminal-auth": {
                             "command": "/Users/marc/.local/bin/kimi-code",
                             "args": ["login"], "label": "Kimi Code Login",
                             "env": {}, "type": "terminal"}}

inside the `session/new` refusal
                         "type": "terminal", "args": ["login"], "env": {}
                         <- FLATTENED onto the method, and NO `command`
```

So **the refusal says WHICH method is wanted and the handshake says what
running it would take**, and an operator needs both. A client that renders
only the refusal's copy — which is the obvious implementation, because that is
the reply in front of it — tells the person there is a terminal login and
cannot tell them what to type.

Wringer merges the two by `id`, preferring whichever carries a command, and a
method the refusal names that the handshake never did is shown as it arrived.
Measured end to end afterwards, against the signed-out agent:

```
the agent refused to open a session: session/new was refused:
Authentication required

The agent says it accepts:
  - Login with Kimi account
      Run `kimi login` command in the terminal, then follow the
      instructions to finish login.
      run this yourself, once: /Users/marc/.local/bin/kimi-code login

Wringer does not run any of these for you. Signing an agent in is your act
on your account, and the command above came from the agent rather than
from Wringer.
```

**And the test double was wrong in the same direction, twice.** It first
omitted `data.authMethods` from the refusal, then sent the RICH shape in both
places. Both made it more generous than the agent, and a mutation that
rendered the refusal's copy alone passed against it. The double now sends both
measured shapes.
