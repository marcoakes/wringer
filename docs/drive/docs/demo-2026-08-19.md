# Prose in, an agent works, proof out — 2026-08-19

*A product manager writes a paragraph. A real coding agent writes real code.
The record shows the check that proves it failing before the work and passing
after. Every console block below is pasted from a run that happened; where a
run id, a token count or a wall clock appears, it is the one that run
produced.*

**Four drives of one repository, and they end four different ways.** Two of
those endings are the ones this document exists to show — a REFUSAL that names
what is missing, and a DONE that shows the same check failing first. The other
two are defects the driving found, kept because they are the reason the first
two work.

## 1. The repository, and why it is not a toy

`~/Claude/demo-2026-08-19/project` — a small pipeline runner: a job graph with
dependencies, a runner, a text summary, a CLI. Four modules, four test files,
18 tests green, `ruff` clean. It is a git repository with a bare `origin` on
local disk, so a delivery has somewhere real to go.

It has one convention that matters, and it is written in its own README:

> `tests/` is the suite that must stay green — `pytest -q` runs exactly that.
> `acceptance/` holds executable specs: checks written from a requirement
> *before* it is built. They are red until the feature lands, which is why they
> are not in the default run.

That is not scaffolding for this demo. It is the practice that makes a
red-first record possible at all, and a team that does not have it will not
reach the ending in §4.

**The PRD is four paragraphs of plain English.** No acceptance criteria, no
gate names, no YAML, no file paths, no function names — it is
the document a product manager would actually
write, and it opens:

> When one step of a pipeline fails, everything that was waiting on it runs
> anyway. Support keeps forwarding us runs where a step fell over two minutes
> in and the run carried on for another twenty, producing a wall of errors that
> all trace back to the same thing.

**Is it trivial?** The test stated before it was written: *would a competent
person do this in under ten minutes without thinking?* No. It needs
transitive skip propagation over a DAG, per-step attribution to the *nearest*
failed ancestor rather than the first failure in time, a summary that
distinguishes three states, and an exit code that keeps its old meaning. The
agent's answer to it is in §4 and runs to 70 lines across four files.

```console

[   0.2s] show     workspace

[   0.3s] stopped  stopped

          wring spec: 'judge.api_key_env' names WRINGER_API_KEY, which is not set in
          this environment

=== exit 2 · 3 answers from the operator · 0.3s of machine time ===
```

The verb asks for an endpoint, a model and a worker. It never mentions that
the endpoint needs a key. Three questions, and the fourth thing it needs is
the one it does not ask about — so the first real drive of this window died at
step 3 with a sentence about an environment variable, said to the reader least
able to act on it.

**Fixed, and the fix claims as little as it can.** DRIVE may not read the
environment at all (`test_there_is_no_flag_that_answers_the_approval` enforces
it structurally), so it cannot check whether the variable is set. What it can
do is say what it just wrote down, at the moment it writes it — which is what
the `workspace` step now does, with the variable name derived from the
generated config rather than typed into a sentence.

## 3. Run 1 — the honest ending nobody wanted, and the false sentence beside it

With the key set, the whole chain ran. `claude-opus-5` read the PRD and drafted
a real specification: **ten acceptance criteria, one of them `human: true`,
three tasks with paragraph-long objectives**, and nine required questions.

It proposed **no acceptance check at all** — and said why, in a question of its
own:

> Which existing modules, classes and test files implement pipeline execution
> and the summary, so acceptance checks can be bound to checks that already
> exist in the repository?

That is the drafter obeying its instructions exactly. Its rules have always
told it that a binding must name a file that already exists in the repository,
and **the request never told it what the repository contained.** The rule was
not wrong; it was unsatisfiable. So the plan the product manager approved said
this, nine times:

```console
          HOW EACH PIECE WILL BE PROVED

            Steps waiting directly on a failed step are not executed
              must — NOTHING CHECKS THIS YET. It will be reported as unevidenced
              and it will not be claimed as done
```

and then, one question later — the plan, a yes, and this — the surface said:

```console
[  47.5s] show     gates-already-installed
          The checks that will prove this work are already part of the project, so
          there is nothing to add.
```

**That sentence was false**, and it was said to somebody who had just read the
opposite nine times. `wring plan` returns no diff in three different
situations — nothing proposed, everything already declared, and proposals it
could not express as an edit to the file — and one sentence was standing in for
all three. Only the middle one was true of it.

The rest followed: the loop converged on its first verify having run **zero
worker turns** — both declared gates were green and nothing new had been added,
so there was no failure to hand anybody — and the record read

```
{'evidenced': 0, 'unevidenced': 9, 'gate-failed': 0, 'gate-did-not-run': 0, 'human': 1}
  direct-dependents-not-attempted   unevidenced  unbound
  ...
  summary-readable-at-a-glance      human        human-unanswered
```

Nine criteria with nothing checking them, one waiting on a person, and no code
written by anybody.

**This is the measurement the window existed to take, and it is the one that
decided everything after it.** The chain was not broken. It was blind.

### What the agent actually wrote

Four files, 70 insertions, 8 deletions:

```
 acceptance/chain.json    |  2 +-
 src/pipeline/__init__.py |  3 ++-
 src/pipeline/report.py   | 23 +++++++++++++++++++---
 src/pipeline/runner.py   | 50 +++++++++++++++++++++++++++++++++++++++++++++---
```

The heart of it, verbatim from the agent's own output — a skip that inherits
its blocker so the blame lands on the nearest real failure:

```python
def _blocking_failure(needs, status_of, blocker_of) -> str | None:
    """The failure this job was waiting on, or None if it may be attempted.

    A job blocked by a job that was itself skipped inherits that job's
    blocker, so the blame lands on the nearest actual failure upstream.
    """
    for need in needs:
        status = status_of.get(need)
        if status == FAILED:
            return need
        if status == SKIPPED:
            inherited = blocker_of.get(need)
            if inherited is not None:
                return inherited
            return need
    return None
```

Nobody in this programme wrote that. Wringer never writes code; it asked the
questions, demanded the proof, and refused the parts that had none.

## 5. Run 3 — a check that could not fail, named while it still mattered

Run 2's binding was a good one. This run is what happens when it is not.

An engineer hand-writes the sidecar — the offline path `wring spec` itself
describes — and binds "steps not depending on the failure still run" to
`pytest -q tests`. That is the repository's own suite with a directory
argument. It is **green today**, so no amount of work can make it fail. It is
also *not* byte-identical to the declared `test` gate, so the duplicate rule
does not catch it.

```console
[   0.3s] confirm  try-gates
          Those checks have not been run yet: bind-independent-steps.
          Shall I try them against the project as it stands, before you decide? A
          check that already passes cannot show the difference this work makes.
   --> yes
[   0.5s] show     gates-tried
          I ran them against the project as it stands: bind-independent-steps.
          bind-independent-steps — This check already passes against the project as
          it stands, so nothing the work does can make it fail — which means either
          the requirement is already met, or this check cannot tell the difference.
          Is this requirement already met, or does it need a different check?
[   0.5s] confirm  install-gates
          That change adds: bind-independent-steps.
          Shall I add those checks to the project?
   --> no
[   0.5s] stopped  stopped:gates-declined
          Nothing was built, because the checks that would prove the work were not
          added. Nothing in the project changed.
```

**That is the whole point of this slice.** On 2026-08-17 the same fact reached
the operator five seconds *after* they had approved the gate, at the handover,
when nothing could be done with it. Here it arrives at the question, the person
uses it, and the answer changes. The sentence is the board's, verbatim; DRIVE
supplies the measurement and never the meaning.

**It asks before it runs anything**, and that is deliberate. The command was
written by a model, and `.wringer.yaml` is the only file that puts a command in
Wringer's mouth. Running one before any approval would execute unapproved
model-authored shell on the operator's machine — and would still have run it if
they then said no.

## 6. What driving it FOUND, including the thing that should worry you

**The agent edited a file its own acceptance check reads.** Among the four
files it wrote is `acceptance/chain.json`, the fixture
`test_skip_downstream.py` executes:

```diff
-  "docs": {"command": "echo docs-built"}
+  "docs": {"command": "echo building docs"}
```

The change is harmless — that string is not asserted on, and the check still
decides the same thing. That is luck, not a guarantee. What matters is
everything around it:

- the product manager had answered the question about that exact file, and the
  answer reached the worker's brief **verbatim**: *"it must NOT change as part
  of this work. The team wrote it before building on purpose. A check edited by
  the same change it is judging proves nothing"*;
- the loop's own record **names the file as it is written**:
  `writing acceptance/chain.json`;
- and the criterion came back `evidenced` anyway.

Nothing refused, nothing warned, and nothing in the record would have told
anybody. The `arrived-with-the-work` guard did not fire, correctly by its own
terms — the file was not *created* by the change, only modified. This is
`SPEC_VACUITY` §5a's inherited blind spot, and it has now been demonstrated on
a real run with a real agent rather than argued about. **It is not fixed here.**

**Four required criteria were left unbound, and unbound does not refuse
delivery.** `refuses=False` on every one of them. Only the human criterion held
the handover. A specification whose criteria are mostly unchecked is reported
honestly on the board and in the plan — but the record's *refusal* rests on one
human row, and that is worth knowing before relying on it.

**Nothing records what the agent's turn cost.** See §7.

**One verify arms one gate.** `wring verify` stops at the first required
failure, so this scenario only works because `lint` and `test` are green at
baseline and the bound acceptance check runs last. A repository whose suite is
red for an unrelated reason would never reach the bound gate, and every
criterion below it would read unevidenced.

## 7. What it cost, itemised

Two drafting calls, from the `response.json` each run wrote:

| run | model | in | out | total |
|---|---|---|---|---|
| run 1 | `claude-opus-5` | 1,405 | 3,562 | **4,967** |
| run 2 | `claude-opus-5` | 1,742 | 3,620 | **5,362** |

**10,329 tokens recorded.** Run 3 made no model call at all — it reused run 2's
drafted spec, which is why it took 0.6 seconds.

**The worker's turn is NOT recorded by anything, and that is a gap rather than
a rounding error.** The agent holds its own session with the endpoint; Wringer
records that a worker ran, what it printed and which files it wrote, but no
token count, because none crosses the ACP wire. What is on disk is the
6,379-byte brief it was handed and the four files it wrote back. **No number is
claimed for it here**, and a supervision layer that meters its drafter and not
its agent is worth fixing.

No corpus row was run. That is a pre-registered instrument and it is Marc's
alone.

|---|---|---|---|
| machine time | 48.5s | **142.8s** | 0.6s |
| total, including the operator thinking | 195s | 262s | 21s |

Of run 2's 142.8 seconds, **~50s is the drafting call** and **~91s is the

chain — ten steps, a rendered board, a refusal — is under two seconds.

**The operator's answers were given by a person reading each step**, not by a
lookup table: the relay writes each question to a file and blocks until
somebody answers it. The nine drafted questions were answered as a batch after
all nine had been read, which is how they arrive; **no `confirm` was ever
pre-answered**, because those three yes/no decisions are the interlock this
whole surface exists to protect.

### Containment

**The worker ran UNCONTAINED.** `podman` is running on this machine and was not
used. The reason is not cost: **`wringer-drive` has no channel for declaring
containment at all** — it generates `judge:`, `run:` and `deliver:` sections and
nothing else, so a product manager driving with one verb runs their coding
agent uncontained by construction, and cannot choose otherwise without opening
an editor. Nothing here may be read as a containment result, and
`SECURITY.md`'s matrix gains a second uncontained row rather than a silent one.

## What this does NOT show

One repository, one scenario, one language, one agent, one machine, one
afternoon. The drafter is non-deterministic and asked a different set of
questions on each of the three drafting calls this window made, so the numbers
above will move.

**Nothing about wrong fixes.** Q1's ceiling binds every sentence here: the
record shows that a stated criterion could fail and was made to pass. It does
not certify that the change is the one anybody intended, and §6 is a
demonstration of exactly that gap rather than a claim against it.

**Nothing about vendor agents.** The worker is a minimal ACP agent written for
these captures, speaking real JSON-RPC to `wringer.acp` and asking a real model
for the repair. Gemini CLI, Goose and Kimi are not installed on this runtime
and none was exercised.

**Nothing about containment**, per above.

**Nothing about a delivered merge request.** No run here reached one. Run 2 was
held by a required human criterion, and no package in this programme will write
the judgement that would release it — which is a live open question, not an
oversight.

**No stranger has read this page.** A cold-read pack exists and has not been
run.

**Nothing about how a PRODUCT MANAGER experiences the interview** (added
2026-08-19). Every answer above is an engineer's, so the register, the length
and the confidence of these answers are not evidence about the audience — see
the note under the table at the top. One real product-manager drive has since
