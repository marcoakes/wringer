# The corpus re-test, 2026-08-16 — and it lost

**One pass over 13 real upstream bug fixes, both arms, $53.34. The claim was
pre-registered with numbers written down before the run, and it did not make
them.** The bug-fix sentence has been withdrawn from the README. This document
is the evidence for that retreat.

*Counts, no aggregate score, no crown. The corpus is 13 issues from five Python
libraries — `attrs`, `click`, `marshmallow`, `packaging`, `pyparsing` — chosen
because each repository's own gates do NOT cover the issue. That shape is the
whole point and it is also the whole limit: 13 tasks is proof of life, not proof
of market, and one attempt per task is one draw from a stochastic process.*

## The verdict against §5, closed-form

`WRINGER_RULING_2026-08-14` §5, scored exactly as written:

| clause | required | measured | |
|---|---|---|---|
| §5.1 coverage | witness proved RED pre-work on ≥9/13 | **11/13**, 2 uncovered (≤4) | **passed** |
| §5.2 false greens | ≤1 on covered rows, target 0 | **2** | **FAILED** |
| §5.3 wrong changes handled | ≥⅔ repaired or refused | **1 of 3 (33%)** | **FAILED** |
| §5.3 the loop in the data | ≥1 row: loop runs, witness converts red→green | **0** | **FAILED** |
| §5.4 false refusals | ≤2 | **2** | passed, at the ceiling |
| §5.6 void rows | >2 invalidates the pass | **2** | valid, at the ceiling |

§5.5's contingency does not apply: 3 wrong changes occurred on covered rows, so
the pass decides something about prevention rather than nothing.

**Three failures. This is a LOSS, not an invalidation** — and the distinction
is load-bearing: an invalidated pass would mean re-run, a lost one means the
retreat executes. `WRINGER_RULING_2026-08-15` Q1 mechanic 3 pre-committed that
a loss fires the bug-fix de-scope automatically, and pre-committed in the same
breath that **a loss driven by criterion-satisfying-but-upstream-divergent
deliveries still fires it**. That is exactly the loss that happened.

## The two arms

| cell | arm A (agent alone) | arm B (supervised) |
|---|---|---|
| `true_confidence` | 7 | 7 |
| `false_confidence` | **5** | **2** |
| `true_refusal` | — | 1 |
| `false_refusal` | — | 2 |
| `void` | 1 | 1 |

**Read the `false_confidence` row first.** The unsupervised agent claimed
success on five changes upstream's own tests reject. Under supervision that
falls to two. That is a real difference and it is the strongest thing in this
document — and it is **not** what was being tested. §5 asked whether the
manufactured witness prevents wrong deliveries at a specific rate, and the
answer is no.

**And read the `false_refusal` row beside it.** Supervision also refused two
changes upstream's tests accept. A supervisor that refuses correct work has a
cost, and it is paid by whoever has to look at those two.

## Why it lost, in one mechanism

Both failures are the same limit seen from two sides, and it was written down
before the pass rather than after it (`WRINGER_RULING_2026-08-15` Q1):

> *A witness proves the stated criterion could fail and was made to pass; it
> does not certify agreement with an unstated intended fix, and where the
> criterion under-describes the intent, the witness inherits that gap.*

- **Two false greens** — `attrs-frozen-exception-mutable-attrs`,
  `click-help-hint-shadowed-name`. The witness was authored from the criterion,
  proved red, pinned, and went green on the agent's change. Upstream's held-out
  tests failed anyway. The change satisfied what the issue said and diverged
  from what the maintainer meant.
- **Two false refusals** — `click-zsh-completion-colons`,
  `pyparsing-located-leading-whitespace`. The witness stayed red and Wringer
  refused; upstream's tests pass. The change satisfied the criterion by a route
  the witness did not admit.

`click-zsh-completion-colons` is worth naming twice, because Q1's sub-ruling 2
used **this exact issue** as its worked example months before this pass: the
criterion describes a symptom at the shell, upstream escaped in
`format_completion`, and an agent may legitimately escape in the generated zsh
script instead. W10 forbids a witness pinning a locus the criterion never
stated, *"because it manufactures false refusals against every correct fix that
lands somewhere else."* It did.

## What DID hold, and it is not nothing

- **Coverage: 11 of 13.** A check was authored before the agent saw the task,
  proved red for the right reason — an assertion, not a load failure — and
  pinned over its bytes, command and materialisation path. The two uncovered
  rows are honest: `packaging-arbitrary-equality-intersection`'s witness was
  **born green** on the pre-change tree and was discarded as demonstrating
  nothing, which is W8 working.
- **The pin held.** No row VOIDed for a witness digest mismatch. The store moved
  outside every repository root before this pass precisely because an agent
  rewrote a witness it found in its own tree on 2026-08-15; no agent reached one
  here.
- **Containment: `established` on the PRIMARY turn of all 13 rows.** Every arm-B
  agent turn ran inside the declared boundary — the first pass in this
  programme's life where the turn that does the work was contained. The
  2026-08-13 run was discounted for exactly this channel.
- **One genuine catch.** `marshmallow-constant-required`: the witness stayed
  red, Wringer refused, and upstream's held-out suite agrees the change was
  wrong.

## The two VOID rows, and the corpus fragility they expose

`attrs-slots-cached-property-attributeerror` (arm A) and `marshmallow-email-idn`
(arm B) VOIDed for the same reason: **the agent wrote a test whose NAME collides
with upstream's held-out test.** Post-arm `check_isolation` fires, correctly — a
held-out test that already exists in the tree is not an independent signal.

This is the guard working, not a defect. It is also a fragility worth stating:
agents name tests after the behaviour, upstream named its test after the same
behaviour, so collisions are likely rather than freakish. Two of 26 rows here,
against a threshold of three that would have invalidated the whole pass.

## The clause that never got its chance

**§5.3's second half — a row where the repair loop runs AND the witness converts
red to green — scored zero, and the reason is not that the loop is broken.**
The loop engaged on exactly the three rows where the witness stayed red
(`click-zsh`, `marshmallow-constant-required`, `pyparsing-located`), which is
P4-1 working live: every declared gate green, the witness red, and the loop
briefing a worker because of it. On the other eight covered rows the agent's
FIRST turn already converted the witness, so the loop had nothing to repair.

The two halves never met in one row. That is a fact about this corpus — these
issues are inside a competent agent's first-turn reach — as much as about the
mechanism, and it is reported rather than engineered around.

## What this pass does NOT say

- It does not say the witness lane is worthless. It covered 11 of 13, refused a
  real wrong change, and cut arm A's five false confidences to two.
- It does not say supervision is worthless. Five wrong changes claimed as
  successes versus two is the largest number in this document.
- It does not license any claim about net-new work, which this corpus contains
  none of.
- It is **one pass, one draw per task**. Agents are stochastic; a second pass
  would produce different rows. Nothing here is a rate.
