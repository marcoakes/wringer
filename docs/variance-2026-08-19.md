# What four identical drafting calls disagree about (2026-08-19)

> **CORRECTION, 2026-08-19, same day — this document's first version was
> WRONG, and wrong in the direction it was warning about.** It said ten
> criteria across three runs carried a buried decision, and that run 2 was a
> "negative control" that asked instead of deciding. An adversarial review of
> SPEC_PMPLAN_V0 checked the claim against the captures and found that **run 2
> buries FOUR decisions under a fourth phrasing — `Decision to approve:`** —
> which the substring this document recommended (`decision taken`) does not
> match. The true count is **14 across all four runs**, there is **no negative
> control**, and the recommended detector finds 10 of 14.
>
> The correction is left visible rather than rewritten away, because the
> mistake is the finding. Twice in one day a phrase was matched against these
> same four files and declared sufficient: first run 1's own sentence (4 of
> 14), then a widened substring (10 of 14). Four rolls produced four phrasings.
> **The detector's ceiling is unknown and there is no reason to think a fifth
> roll would not produce a fifth phrasing.** §3 below is rewritten; §2's
> per-browser observation stands and is unaffected.

Four `wring spec --send` calls, **the same PRD**, the same model, the same
request — measured because SPEC_PMPLAN_V0 needed to know what a product manager
is actually consenting to when they approve a drafted plan.

The four replies are captured byte for byte at
`tests/replies/2026-08-19-arcade-run{1..4}-drafter-reply.json`. Nothing here is
reconstructed; every number below is read from those files.

**The input really was identical.** `prompt_tokens` is **2206 on all four
runs**. So every difference in the table is sampling variance, not a different
question asked four ways.

| run | questions | required | criteria | tasks | buried decisions | out tokens |
|---|---|---|---|---|---|---|
| 1 | 2 | 2 | 9 | 3 | **4** | 4813 |
| 2 | 2 | 2 | 10 | 3 | **4** | 5193 |
| 3 | 2 | 2 | 12 | 4 | **3** | 5100 |
| 4 | 3 | 3 | 11 | 3 | **3** | 5364 |

Total spend for the measurement: 8824 prompt tokens, 20470 completion tokens.

## 1. The question cap holds — and it is a prompt, not a guard

Required questions came back **2, 2, 2, 3**. The rule *"AT MOST THREE
QUESTIONS"* lives in `render_request`'s prose (`spec.py:661`) and **nothing at
parse time enforces it**. It held here. It also held on 2026-08-17 that a
binding must not repeat a declared gate, right up until the drafter proposed
`pytest -q` as both in the same reply.

Prompts are not guards. SPEC_PMPLAN_V0 ruling 3 makes this one a guard.

## 2. What the PM is asked depends on the roll

Every run asked `what-counts-as-played`. After that they diverge:

- run 1 — `clearing-history`
- run 2 — `per-browser-memory`
- run 3 — `retired-game-in-history`
- run 4 — `memory-scope`, `clearing-history`

**Run 2 asked whether history is per-browser. Run 1 decided it silently** and
wrote the decision into a criterion's test guidance:

> *"Decision taken without asking: this is per-browser only — there are no
> accounts, so the list does not follow a person to another device or browser,
> and that is acceptable."*
> — run 1, criterion `survives-tab-close`

Same PRD. One PM is asked; another is not, and finds out only if they read the
`guidance` field of an acceptance criterion. **What a person consents to
depends on a die they cannot see.**

## 3. The drafter writes assumptions into a field that is not for them — and labels them differently every time

The request tells the drafter to *"write your decision into the criterion it
affects"* (`spec.py:671`) and gives it **no field to put a decision in**. So it
invents one, in prose, inside `guidance`.

**Fourteen criteria across ALL FOUR runs carry such a decision** — and every
run labels them its own way:

| run | phrasing it chose | criteria |
|---|---|---|
| 1 | `Decision taken without asking:` | 4 |
| 2 | `Decision to approve:` | 4 |
| 3 | `Decision taken unless overruled:` | 3 |
| 4 | `Decision taken unless the memory-scope question says otherwise:` / `Decision taken:` | 3 |

**Four rolls, four phrasings. That is the finding, and it survived two attempts
to reduce it to a substring:**

| detector | finds | misses |
|---|---|---|
| `decision taken without asking` — run 1's own sentence | 4 of 14 | runs 2, 3, 4 entirely |
| `decision taken` — the "corrected" substring | 10 of 14 | run 2 entirely |

Both were written against these same four files, hours apart, and both were
believed sufficient at the time. The second was published here as a measured
fact, complete with a "negative control" — run 2, which turned out to bury four
decisions under a phrasing nobody had looked for. An adversarial review of the
spec caught it by checking the claim rather than the code.

**So the honest statement is a lower bound with no known ceiling.** Any count
produced by matching prose is *at least this many*; nothing here licenses
"and no more". No structural check can replace the matching, because nothing
distinguishes decision prose from check prose except its meaning — which is
also why widening the pattern is not convergence, just a bigger net with
unknown holes.

The consequence for anything built on this: **a detector's silence is not
evidence that a draft took no silent decisions**, and a run reported clean has
not been shown to be clean. It is written down here so nobody later reads a
clean run as proof of one — which is exactly the error this document's first
version made about run 2.

## 4. What this measurement does not say

It does not say four runs are enough to characterise the variance — they are
not, and the numbers above are a sample of four, not a distribution. It does
not say 14 is the number of decisions these four drafts took silently; 14 is
how many they **labelled** in a way somebody thought to grep for, and the
correction above is what happens when that distinction is dropped. And it does
not say the criteria counts (9, 10, 12, 11) reflect different amounts of work —
nobody built all four.

What it does say is narrow and enough: **on one unchanged PRD, the set of
decisions a product manager is invited to make is not stable, and the decisions
they are not invited to make are recorded where they will not read them.**
