# Brief quality — what the worker is actually told

*2026-08-10. The factory dry run measured a gap; this is the same scenario
re-driven with the gap closed. **Both transcripts below came out of `wring
run` on a real repository today.** Neither was written by hand, and this file
is generated by splicing them in, because a document about what a command
prints is worth nothing if a person typed the printout.*

## The finding

From [the dry run](factory-dry-run.md) §4: the loop's brief was thirty-five
lines about a failing gate, with **not one word about the feature**. `wring
plan` knew the objective and did not pass it on; `wring run` knew what was
broken and did not know why. Between those two is exactly where a PM's spec
should turn into instructions, and nothing carried it across.

That matters more here than it would elsewhere. Wringer never writes the
code — a worker does — so **what the worker is told is this product's output
quality**, and it was a bug report about somebody else's missing dependency.

## The scenario, re-driven

The dry run's repository, rebuilt: a working `reports` module, a passing
test, and a PM's spec asking for CSV export — four acceptance criteria, one
of them `human: true`. Two acceptance gates hand-written and bound with
`proves:`, and a third criterion with no gate at all, because that is the
honest state of a repo the day a spec is approved.

The repo's own `test` gate runs first and fails on a missing pytest, exactly
as it did on the day of the dry run. **Both runs below therefore brief a
worker about the same irrelevant failure**, which is the point: the failure
is the control, and the objective is the variable.

The two runs differ by **one boolean** in one file:

```yaml
approved: false     # then: true
```

Nothing else in the repository changes between them — not a gate, not the
worker, not a line of code.

## What changed, and what did not

- **A repo without an approved spec gets the same brief, byte for byte.** Not
  "similar" — the same first line, the same headings in the same order, and
  not one word from any spec. `test_without_an_approved_spec_the_brief_is_the_one_it_always_was`
  pins it in both states (no spec at all, and a spec awaiting approval), and
  it was watched failing against a build that ignored approval.
- **The opt-in boundary is approval**, exactly as acceptance's is
  (`SPEC_ACCEPT_V0.md` ruling 8) — and it is acceptance's own reader,
  `accept.read_spec`, so the two cannot drift apart. A drafted spec nobody has
  read yet has no force over what a worker is told, for the same reason it has
  none over delivery.
- **No model is asked anything.** The section is assembled from
  `wringer.spec.yaml`, `.wringer.yaml` and the brief file `wring plan` already
  wrote. `wring run` still makes no LLM call and no network call.
- **The task's brief arrives inlined, not named.** `wring fleet` sets
  `WRINGER_TASK_BRIEF` to an absolute path, and before this a worker reached
  the objective only if somebody had written it to open that variable. The
  file's contents now travel in the brief; the variable stays set, and
  `test_the_task_environment_still_reaches_the_child` is the first thing that
  ever held it there.
- **The quoted brief is fenced.** Found by reading the first real output
  rather than by predicting it: `wring plan` writes briefs with `#` headings
  of their own, and pasted bare they became peers of this document's, so
  "Decisions already made" read as a sibling of "What finishing means". The
  fence is sized to the file, because a brief about markdown carries fences
  too.

## What this does not claim

- **The loop is still wrong about this failure.** Both runs above burn their
  whole budget briefing a worker to repair a missing pytest — an environment
  fault, not a repair job. That is F6 in `WRINGER_FACTORY.md`, untouched here
  and blocked on a frozen reason enum. The brief now says what is being built;
  the loop still does not know why it cannot build it.
- **No gate was authored, proposed or bound.** `amounts-two-decimals` reads
  `UNBOUND` above and it stays that way. Who writes the acceptance gate for a
  criterion whose feature does not exist yet is F2, and it has no spec yet;
  nothing in this slice may answer it by accident.
- **Nothing was measured about what a worker does with this.** No agent ran.
  This is evidence about what the worker is *told*, which is a necessary
  condition for building the right thing and nowhere near a sufficient one.
- **A fleet task in a subdirectory still gets the old brief.** The spec is
  read from the loop's own root, like every other root-scoped read in the
  program, so a task whose `dir:` is not the repository root cannot see
  `wringer.spec.yaml` and falls back — correctly, and unhelpfully. Worktree
  mode is unaffected, because a worktree is a whole checkout.

## Reproducing it

The two runs above are one repository and one edited boolean. In any repo
with an approved `wringer.spec.yaml` and a failing gate:

```bash
wring run
```

The brief handed to the worker is written to the loop bundle at
`.wringer/loops/<id>/iterations/001/brief.md`, and it is the same bytes the
worker's `{brief}` placeholder points at.
