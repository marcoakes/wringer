# The gate is dead and every tick is green

*`wring health` reads the evidence your runs already wrote and answers, per
gate, the question no dashboard asks: **is there any evidence this check can
still fail?** A gate that cannot fail is not a gate — `--prove` says that
about one run; this says it across time.*

This is [specs/SPEC_HEALTH_V0.md](specs/SPEC_HEALTH_V0.md) end to end. Everything below
is **real captured output** from a scratch repository, produced by
`scripts/demo.sh` — regenerated by running it again, never edited by hand.

---

## The recording

![wring health: the gate is dead and every tick is green](health.svg)

Read it in four beats.

**1. The gate fails for real.** `multiply` is wrong and a test says so. This
is the only moment in the whole recording where anything is red, and it is the
moment that matters: the check has *demonstrated* it can discriminate, with a
receipt.

**2. `wring health` says `alive` — from one run.** One demonstration is enough
to believe a demonstration; no number of runs is needed. (Thin history is only
a problem for the *negative* claim. That asymmetry is the report's third
limit, and it is why the first beat is filmable at all.)

**3. A worker "fixes" it by neutering it.** `wring run` hands the failure to a
worker, the worker rewrites the failing assertion into a tautology, and the
gates go green. **From this instant the check is dead and nothing anywhere
says so.** The loop converged. The bundle is valid. The run passed.

**4. Twenty-five more real runs later, `wring health` says `zombie`.** Every
one of those runs passed. Every one wrote a valid bundle. Every dashboard on
earth shows twenty-five green ticks — and the vitality table says there is no
recorded evidence, anywhere in the window, that this gate can still fail.

Nothing was faked to get there. The twenty-five runs really execute, as one
displayed-equals-executed shell step, because faking time in a recording about
decay would be exactly the dishonesty this tool sells against.

## The verdicts, and what each refuses to claim

| verdict | means, exactly | never means |
|---|---|---|
| `alive` | the window holds a genuine failure or a proven-sensitive row, **at any history depth** | "this gate is well designed" |
| `zombie` | at least ten qualifying runs in the window and **no recorded evidence it can fail** in any of them | "delete this gate" — a stable codebase keeps good gates green for months |
| `untested` | fewer than ten qualifying runs, none of them positive — too thin to say anything | "probably fine" |
| `retired` | no longer the contract; history shown, **no verdict claimed** | "this gate was bad" |

The window is the newest **25** qualifying runs and the history floor is
**10**. Both are constants, not config keys: a tunable threshold is a knob
whose only realistic use is making zombies disappear before a release, and a
window key is the same knob wearing recency.

**A genuine failure is `status: failed` *and not a timeout*.** Both halves
matter — in the published gate-result format a timeout already records
`failed`, so a predicate testing status alone would rank a gate that has only
ever died of slowness as the most alive thing in the report. Timeouts surface
as drift instead.

## The coverage statement comes first

A health tool that silently skips unreadable history is itself a narrowing
check — the exact defect this command exists to catch, one level up. So the
report leads with what it read and what it could not:

```console
searched 2 roots · read 29 bundles · skipped 0 · duplicate 0
  28 runs, 1 loop, 0 bench (bench evidence decides nothing)
```

Every skip is itemised with a reason, every duplicate names both paths, and
`discovered == read + skipped + duplicate` is pinned by a test. A bundle
dropped before it was classified looks exactly like a clean run, which is why
counting the skip list against itself is not enough.

**Bench evidence is read, labelled, and decides nothing.** `wring bench`
refuses to start unless the baseline is red, so every bench guarantees a
failed row for every required gate on a tree nobody changed — under the same
identity as your real gates, in enough bundles to fill the window by itself.
Counting it would make gates read `alive` on a staged repair exercise, which
is a way to make zombies disappear.

## Identity: a gate is `(id, command)`

Change the command and the record starts over. Editing is *how* checks most
often narrow — a probe keeps its name while its coverage shrinks — so
continuity across an edit is not inferred and is not granted. The prior
definition appears under **retired** with its history intact and no verdict.

That also closes a hole: the window is scoped to a pair's own runs, so a gate
that is renamed or deleted stops accumulating and its window *freezes* at
whatever it last held. Without `retired` it would read `alive` in perpetuity,
from evidence of arbitrary age, for a check that no longer exists.

## The tooth

```bash
wring health --strict
```

Exit 1 if any **required** gate is a zombie, and nothing else. Optional gates
get verdicts and never decide outcomes; a retired pair cannot be required by a
config that no longer declares it. Requiredness is read from `.wringer.yaml`,
never from the recorded `optional` flag — that flag is mutable across a pair's
history and one window can hold both values.

Without `--strict`, health exits `0` whatever it says. It is an observer: an
instrument that exited non-zero after successfully measuring decay would be
reporting its own state with the patient's chart.

## In CI, where somebody is held to the answer

The shipped recipe in [`examples/github-actions/`](../examples/github-actions/)
runs it after verify and renders the table into the job summary.

**It needs history, and a fresh checkout has none.** `.wringer/` is gitignored,
so the job holds exactly the one bundle `wring verify` just wrote — one run,
below the floor, so *every gate reads `untested`*. That is the true answer for
a repo with no record rather than a defect, and it is why the recipe restores
a history directory across runs with `actions/cache` and points `--from` at
it. Wringer opens nothing: it reads a directory the workflow populated,
exactly as `--from` reads one anywhere.

## What this does not say

Four limits print with every run and ride in `--json`, because a vitality
report is exactly the artifact a reader will inflate:

1. **Health reads recorded evidence.** A gate can be well designed and still
   read `zombie` — the claim is about the record, not the gate.
2. **Only declared gates are visible.** Checks outside `.wringer.yaml` —
   scripts, CI steps, hand-kept lists — are beyond this instrument, and they
   narrow too.
3. **Thin history cannot support `zombie`.** It can support `alive`.
4. **A sensitive row proves the gate's result changed with the tree, not that
   the change was honest.**

The fourth is the sharpest, and it is aimed at this page's own demo. An agent
that deletes an **already-failing** assertion makes the gate genuinely fail on
the pre-change tree, so `--prove` records `sensitive: true` — for the wrong
reason. That is
[specs/SPEC_VACUITY_V0.md](specs/SPEC_VACUITY_V0.md) §5a's stated blind spot, and
health reads sensitivity as vitality, so **health inherits it whole**.

Which is why the recording above never runs `--prove` on the neutering change.
Had it done so, the very act of killing the gate would have minted a fresh
vitality receipt for it, and the table would have read `alive` for the next
twenty-five runs. Closing that would need something that reads diffs for
*meaning* — an LLM — which is a binding non-goal here. Stating it is the
honest option, so it is stated on the report itself and not only here.
