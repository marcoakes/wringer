# The first corpus — 2026-08-13

**This is evidence, not a spec.** It records the first time Wringer was measured
against real upstream bug fixes with a real model. It is not rewritten;
corrections arrive as postscripts.

Contract: [SPEC_BENCHMARK_V0.md](../SPEC_BENCHMARK_V0.md). Selection rule:
[benchmark/CORPUS.md](../benchmark/CORPUS.md), written and committed before any
task that costs money had been run. Manifest:
[benchmark/corpus/corpus.yaml](../benchmark/corpus/corpus.yaml). Rows:
[benchmark/corpus/results/](../benchmark/corpus/results/).

**13 tasks · 5 repositories · 2 full runs · 52 rows · $76.99 reported.**

---

## 1. The claim lost, and it lost for a reason worth more than a win

> `delivery_eligible` is a better predictor of *actually correct* than *the
> agent says it is done*. — SPEC_BENCHMARK_V0 §1

| | run 1 arm A | run 1 arm B | run 2 arm A | run 2 arm B |
|---|---|---|---|---|
| true_confidence | 9 | 10 | 8 | 10 |
| **false_confidence** | **4** | **3** | **5** | **3** |
| true_refusal | 0 | 0 | 0 | 0 |
| false_refusal | 0 | 0 | 0 | 0 |

Arm B looks one or two rows better in both runs. **It is not, and the artifacts
say why:**

- **`wring deliver` said YES on 26 of 26 arm-B rows**, across both runs,
  including all six whose change fails upstream's held-out tests.
- **The repair loop never ran.** Every arm-B loop converged at iteration 1 with
  **zero worker turns** — the first `wring verify` passed, so there was never a
  failing gate to brief anyone with. Committed and checkable for run 1's
  thirteen bundles (`results/loops/`, whose `head_sha`s match run 1's rows);
  run 2's were observed the same way at the time and are not committed, so read
  26 as **13 measured, 13 reported**.

A predictor that never says no predicts nothing. Arm B's claim was constant-true,
so arm B's cell was decided entirely by its own agent draw — which makes the
arm A / arm B comparison two independent draws of the same agent, and the
one-to-two row gap sampling noise. **4 of 13 tasks changed verdict between the
two runs, and `marshmallow-email-idn` swapped sides outright** (arm A failed in
run 1, arm B failed in run 2). That is what noise looks like.

**A caveat neither the run nor the first draft recorded.** Both passes ran while
`~/.local/bin/wring` was pinned at **0.2.0** (fixed later the same night, after
run 2 finished). The harness's own verdicts call `sys.executable -m wringer`, so
every number above is 0.3.0's — but an agent that shelled out to `wring` inside
its tree to check itself got a version behind, and that belongs in the row
deviations rather than a footnote.

## 2. Why the verdict was constant, measured rather than argued

**On RUN 1's thirteen arm-B trees**, `wring verify --prove` was run afterwards.
It costs nothing and it is unanimous — **13/13 `gates_vacuous`, `sensitive:
false` on every gate**. Run 2's trees were not swept: the gate and the base
commit are identical so the verdict is near-certain there too, and this document
does not claim a measurement it did not make.

> every required gate passed without the change too (test), so they proved
> nothing about it — write a test that fails without your change

So the delivery verdict was decided by a configuration flag rather than by the
change:

| `run.prove` | `wring deliver` | discrimination |
|---|---|---|
| off — what actually ran | **yes** to 13/13 | none: constant yes |
| on — measured afterwards | **refuses** 13/13 | none: constant no |

**Both are the same fact seen twice: the repository's own suite was green before
the change and green after it, on every task.** It could not testify about the
fix either way.

And this is not an accident of the corpus — it is what the corpus was *selected
for*. `CORPUS.md` §3 requires tasks where the repository's declared gates do not
cover the issue, because that is where a good agent plausibly declares success
wrongly. Wringer's only evidence *is* those declared gates. **The corpus selected
precisely for the condition under which this supervision path has nothing to
say**, and that tension between §3 and the claim was invisible until real money
was spent against it.

Do not read this as "just turn `--prove` on". SPEC_VACUITY's pre-change tree
drops the agent's new tests along with its fix, so on this corpus `--prove`
refuses a *correct* fix as readily as a wrong one. Neither setting is a
predictor. What would be one is a gate authored for the criterion and required
to be RED before the work — which is exactly what
[SPEC_GATEGEN_V0](../SPEC_GATEGEN_V0.md) already says and what this corpus
did not exercise.

## 3. The corpus leaked the answer, and that is the headline finding

An adversarial audit of run 1 — five independent readers told to refute the
conclusion, then a sixth asked what they all missed — found what the isolation
checks could not see.

**`build.py` cloned each repository and checked out the base commit. A clone
brings the whole history.** The working tree sat at the base commit while
upstream's fix — the thing the task asks the agent to write — waited in `.git`,
reachable by sha and usually by tag. Every isolation rule in the harness looks at
the working tree or at a command string. None of them can see an object store.

Measured, in run 1:

- `git cat-file -t <fix_sha>` resolved in **all 13** task trees.
- **9 of 26 rows** carried a contamination signal; **8 of those 9 scored
  `true_confidence`**.
- **Both arms** of `click-zsh-completion-colons` found the fix commit with
  `git log --all --grep`.
- Three arm-B rows fetched upstream directly: a `.patch` (which *contains* the
  held-out test file), a PR diff, and a post-fix copy of the very source file
  the task asked to change. On `marshmallow-email-idn` the resulting change was
  **byte-identical to upstream's**, including choices no independent attempt
  would match — and that was the single task where run 1's two arms differed.

A second leak was mine: five task statements opened with a `Source: <upstream
issue or PR>` line I added while assembling the corpus. A pointer straight at the
answer, in the text handed to the agent.

**Run 2 NARROWED both. It closed neither, and the first draft of this document
claimed it had.** An independent review reproduced what was left, on a real
corpus tree, on 2026-08-14:

- **`git remote remove` deletes the config entry and nothing else.**
  `.git/FETCH_HEAD` still recorded the mirror it was fetched from, so
  `git fetch "$(sed -n '1s/.* of //p' .git/FETCH_HEAD)" main` brought the whole
  history back and `git cat-file -t <fix_sha>` answered `commit`. One line, no
  guessing. Reproduced here before acting on it. FETCH_HEAD is deleted at build
  time now; the mirror path remains guessable, so the route is narrower and not
  shut.
- **The `Source:` pointer came off 5 of 13 statements.** Eight kept an
  author-added pointer at the upstream issue — three in the identical `Source:`
  shape, two as a title rewritten to `# <repo> issue #N:`. All 13 are clean now
  and a test refuses a statement that carries one.

**And `check_isolation` now runs again AFTER each arm**, because the first check
only ever proved what was true before the agent started.

What *was* narrowed shows: `click-zsh-completion-colons`, which both arms solved
in run 1 after finding the fix commit with `git log --all --grep`, **fails in
arm A in run 2**.

**And the harness now refuses rather than trusting the builder** — a task
declares `forbidden_shas`, and `check_isolation` voids the arm if any of them
resolves.

## 4. What still leaks, and cannot be closed from here

**The agent has a shell and a network, and it needs the network to reach its own
API.** Every task cut from public history points at a repository whose fix is
published.

**The counts here were wrong in the first draft and are corrected.** The detector's
commonest signal was "the log names the upstream repository" — but 12 of 13
statements name it, in upstream's own prose, because that is what a real bug
report looks like. An agent quoting its own brief tripped it. `contamination()`
now ignores a repository the statement already named, which is what its own
docstring always promised ("what the agent went and read THAT IT WAS NOT GIVEN").
Re-measured over the same logs:

| | first draft | corrected |
|---|---|---|
| run 1 rows signalling | 9 of 26 | **7 of 26** |
| run 2 rows signalling | 6 of 26 | **4 of 26** |

So the rule this project already applies to container escapes applies here: if
you cannot prevent it, record that it happened. Every row now carries
`contamination` (schema `wringer.benchmark.v3`). **An empty list is the absence
of a signal this harness knows how to look for, and never a promise.**

The thing that would close it — running the worker inside the container backend
with the network off — is unavailable for the reason `execution.json` already
states: the published image ships no coding agent.

## 5. What the run cost

**$76.99 reported** by the agents themselves, unverified, across two full passes:
$38.78 for run 1 and $38.21 for run 2, over 1.5M and 1.5M tokens. The estimate in
`preflight.py` was $80–400 for one pass; two passes came in under the bottom of
it. Per task per arm the median is about $1.50.

## 6. What this does NOT say

- **Not that Wringer is useless.** It says that on tasks where a repository's own
  suite does not cover the issue, a supervision layer whose evidence is that
  suite adds nothing — which is `demo-narrow-gates`, already shipped as a test,
  now reproduced at scale with a real agent.
- **Not that the agent is bad.** 19 of 26 rows in run 1 and 18 of 26 in run 2
  passed upstream's held-out tests, and one
  of the failures (`click-help-hint-shadowed-name`) satisfies the statement's own
  stated requirement while disagreeing with upstream's implementation — the
  ground-truth false negative §3 of the harness warns about, seen in the wild.
- **Not a rate.** 13 tasks, one draw each per arm per run, and the two runs
  disagree on 4 of them. There is no aggregate here worth quoting.
- **Nothing about docker, Linux, or a corpus with covering gates.** Those are
  unmeasured.

## 7. What has still never been run

- **A corpus whose gates COVER the issue.** Every task here was chosen for the
  opposite. That corpus is the one that could let Wringer win, and it does not
  exist.
- **The gategen path against a corpus** — a gate authored per criterion and
  required red before the work. §2 says that is where the discriminating power
  would have to come from, and no task here exercised it.
- **A task where the repair loop engages.** 26 arm-B runs, zero worker turns.

## Postscript, 2026-08-14 — the rows did not contain the changes, and the changes were nearly lost

Everything above describes 52 agent changes. **This repository held no copy of
any of them.**

A row's `evidence` is `{tree, base_sha, workdir}`. `tree` is an absolute path
into a `/private/tmp` session scratchpad, the changes lived there as
*uncommitted edits*, and a scratchpad is deleted without warning. The corpus
cost $76.99 and produced an artifact that could not show its own work: every
claim in §2 about what the agents did was, until today, uncheckable by anyone
who did not still have the scratch directory mounted.

They were still there. All of them:

| | count |
|---|---|
| rows across both runs | 52 |
| evidence trees still reachable | **52** |
| trees already gone | **0** |
| patches extracted | 51 |
| patches verified applying to their `base_sha` | **51 / 51** |
| rows whose agent changed nothing at all | 1 |

They are committed at
[`../benchmark/corpus/results/patches/`](../benchmark/corpus/results/patches/)
with a manifest binding each patch to its row. `benchmark/harness.py` now
records a row's patch inline as `wringer.benchmark.v4`, so no future run
depends on a scratch directory outliving it.

**Three things the patches say that the rows could not.**

*One.* `packaging-arbitrary-equality-intersection / a_native` in run 2 has no
patch because the agent **changed nothing whatsoever and claimed success**. The
row scored it `false_confidence` on the held-out result alone. SPEC_BENCHMARK's
own limits section predicted this case in writing — "an agent that exits 0
having done nothing is recorded as claiming success" — and here it is.

*Two.* The two runs are not the same kind of data, and the trees prove it
rather than the prose asserting it. Run-1 trees carry **778–3697 commits** of
upstream history; run-2 trees carry **2**. The `.git` leak §5 documents is
visible per row now, as `history_depth` in the manifest.

*Three, and it bounds what the corpus can still be used for.* The 14 wrong
changes with patch content span only **5 of the 13 tasks** —
`attrs-frozen-exception-mutable-attrs`, `click-help-hint-shadowed-name`,
`marshmallow-constant-required`, `marshmallow-email-idn`,
`click-zsh-completion-colons`. The other 8 tasks produced no recorded wrong
change in either pass. Any offline calibration against this set is scored on
those 5: covering nine *tasks* is not covering nine *wrong changes*, and a
check that never meets one of these five has not been tested against a wrong
change at all.
